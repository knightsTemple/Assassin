# 双主角动作 RPG 项目策划案（讨论稿 v0.1）

> 更新日期：2026-09-27  
> 状态：方向讨论稿，供确定范围与原型目标使用；不代表工程中已经实现任何功能。  
> 项目暂定名：《双影》（工作名，可更换）。

## 1. 一句话定位

一款单人第三人称动作 RPG：玩家在同一段冒险中操控两名能力互补的主角，通过潜入、正面战斗、装备成长与据点经营完成任务。首个版本聚焦一块小型关卡和一条完整的“接任务—战斗/潜入—获得奖励—强化—再挑战”循环。

### 设计目标

1. **双主角确实改变玩法**：两人面对同一个敌方据点时有不同的可行路径，而非只是外观和武器不同。
2. **战斗与潜入都有用**：正面战斗更直接，潜入能减少资源消耗并获取情报或额外奖励；两条路线都能通关。
3. **基础 RPG 循环完整**：获得金币与装备，调整配装，购买或出售物品，挑战更强敌人，进度可保存。
4. **范围可控**：优先做可反复体验的 15–30 分钟演示关卡，再决定是否扩展世界、剧情和系统深度。

### 参考边界

“类似《刺客信条：影》”仅理解为“双主角互补 + 潜入/战斗选择”的体验参考。世界观、角色、叙事、美术、关卡、界面和具体机制均应原创，不复刻其受保护的表达。

## 2. 项目假设与待确认事项

当前文档不依赖具体引擎版本、模板、插件、素材或已完成代码。实施前需要核对项目现状。以下是**策划建议**，不是已确认的工程事实：

| 项目 | 暂定方向 | 需要确认的问题 |
| --- | --- | --- |
| 平台 | PC，键鼠优先，后续支持手柄 | 是否有主机或移动端目标？ |
| 视角 | 第三人称跟随视角 | 是否已有角色控制模板？ |
| 模式 | 单人离线、无联机 | 是否计划合作玩法？ |
| 美术 | 写实倾向但采用风格化简化资源 | 团队能提供多少角色、动作、场景资产？ |
| 制作规模 | 先做一块演示关卡 | 个人项目还是团队项目？可投入周期？ |
| 商城 | 游戏内金币商人，不涉及真实货币 | “商城”是否指付费商店？若是，需要另行规划。 |
| 主角切换 | 安全区域和非战斗状态即时切换 | 是否期望战斗中自由切换？ |

## 3. 核心体验与设计支柱

### 3.1 两名主角

主角 A（暂称“影”）擅长机动、侦察和潜入：移动快、擅长绕后、可标记敌人，对轻甲目标有爆发优势；被多人围攻时容错较低。

主角 B（暂称“锋”）擅长正面交战和控制：生命与韧性较高，能格挡、破防和牵制重甲敌人；潜入效率较低、移动较慢。

**共同基础**：移动、翻滚、轻重攻击、受击、交互、使用消耗品、装备管理、升级。共同操作习惯保持一致，差异主要来自战术能力和敌人应对方式。

**切换规则（首版）**：两人共享任务进度、金币、材料和仓库；分别拥有装备栏、生命状态与技能成长。处于非战斗状态、未播放关键动作时可切换。切换后另一人不以独立 AI 同伴形式留在场上，避免首版同时承担伙伴 AI、双人寻路和战斗平衡。战斗内切换列为后续验证项。

### 3.2 可读的动作战斗

敌人攻击要有明确前摇与反馈。玩家通过观察、闪避、格挡或打断获得优势。数值成长能改善效率和容错，但不能代替基本的时机判断。

### 3.3 小范围、可复玩的关卡

同一个据点至少有潜入路线、正门交战路线和一处可以混用两种玩法的侧路。隐藏信息、敌人站位和环境交互带来重玩的理由，不依赖巨大地图填充时长。

## 4. 玩家循环

```text
据点接任务 / 补给
    ↓
选择主角、装备、消耗品
    ↓
进入关卡，侦察敌人与路线
    ↓
潜入、战斗或混合推进
    ↓
完成目标并领取金币、经验、掉落
    ↓
装备 / 购买 / 出售 / 升级
    └────────────→ 挑战更难目标
```

单次任务控制在约 8–15 分钟。失败后从关卡入口或阶段检查点重新尝试，已消耗的资源如何结算需在原型测试后确定；首版建议失败时回滚到进入任务前的状态，避免软锁。

## 5. 首个可玩版本（MVP）

目标是完成一条可从头到尾游玩的闭环，而非堆满菜单和数值。建议验收内容：

| 模块 | MVP 必须具备 | 暂缓内容 |
| --- | --- | --- |
| 角色 | 两名可操作主角；安全状态切换；各自一项独有主动能力 | 战斗中切换、双人协同 AI、大型技能树 |
| 战斗 | 锁定/自由瞄向其一；轻重攻击、闪避、受击、死亡；主角 B 可格挡 | 复杂连招、处决动画矩阵、骑乘 |
| 潜入 | 蹲伏、视野/警戒、绕后击倒、发现反馈；主角 A 可标记 | 大规模人群伪装、复杂光照潜行 |
| 敌人 | 近战杂兵、远程/警戒兵、精英各 1 种 | 大量敌人派系、复杂首领多阶段 |
| 装备 | 武器、护甲、饰品各 1 槽；比较、装备、卸下；品质 3 档 | 随机词条、套装、锻造、耐久度 |
| 成长 | 经验、等级、少量属性点或固定成长；两人分别成长 | 洗点、职业分支、无限等级 |
| 商店 | 金币购买/出售装备及药品；库存固定 | 真实货币、动态市场、每日刷新 |
| UI | 主菜单、HUD、交互提示、背包/装备、商店、任务、暂停、结算 | 完整地图、图鉴、复杂社交 UI |
| 内容 | 1 个据点、1 个主线任务、1 个可选目标、1 个商人 | 开放世界、长篇剧情、多地区 |
| 存档 | 手动或自动存档至少一种；记录任务、金币、角色成长、物品与装备 | 多周目、云存档 |

### MVP 完成标准

从启动游戏到完成任务、取得奖励、在商店买卖、换装、保存并重新进入游戏，整条流程可以独立完成；没有阻断流程的错误。两名主角在关卡中都有明显优势场景，且都能完成主要目标。

## 6. 详细系统设计

### 6.1 角色属性与成长

**建议属性**：生命、耐力、攻击力、防御力、破防能力、潜行效率。首版尽量使用少量直观属性，避免堆叠暴击率、元素抗性等难以感知的数值。

- 生命归零则任务失败或返回检查点；耐力用于闪避、重击和格挡，常规移动不消耗耐力。
- 经验由任务和击败敌人获得，任务奖励占主要部分，防止鼓励反复刷弱敌。
- 每次升级提升基础属性，并提供一个简单选择，例如“生命 +X”或“主要能力 +X”。若开发量受限，先采用固定成长。
- 两名主角等级独立，但任务经验应让未出场角色获得一定比例，避免玩家被迫重复刷级。比例可从 50% 作为测试起点，并由试玩反馈调整。

### 6.2 攻击、防御与伤害

输入层区分轻击、重击、闪避、格挡/特殊能力、锁定目标。受击反馈包括命中音效、受击动作、血条变化和短暂命中停顿；所有反馈应可调节，避免破坏操作响应。

伤害可先按“攻击力 × 动作倍率 − 防御减免”计算，并设置最低伤害。具体公式在手感验证后确定。精英敌人通过招式、站位和破防需求制造挑战，避免只增加生命值。

**状态规则**：攻击、闪避、格挡、受击、死亡具有明确优先级；关键动作是否可取消要逐一定义。闪避的无敌时间、攻击前后摇、耐力消耗均以数据配置，方便调参。

### 6.3 潜入与警戒

敌人状态建议为：巡逻 → 怀疑 → 搜索 → 警戒/战斗 → 脱战。玩家通过蹲伏、掩体和视线盲区接近目标。首版可主要依据距离、视角和遮挡判定，不做复杂实时光照判定。

玩家必须看得懂为何被发现：敌人头顶状态、方向提示与音效同步反馈。被发现后允许转入战斗，不强制任务失败。潜入击倒仅对可击倒目标生效，精英敌人应有清楚的限制提示。

### 6.4 装备与背包

装备数据至少包含：唯一物品 ID、名称、类型、品质、等级要求、主要属性、售价、图标、描述。武器可限制给适配主角，护甲/饰品是否通用待定；界面必须标明限制原因。

品质先设普通、精良、稀有三档。更高品质意味着更好的基础属性或一条简明特性，不引入大量随机词条。背包以格子或列表展示均可，但必须支持排序/分类、比较当前装备、出售前确认。任务物品不得出售。

### 6.5 金币与商店

金币主要来自任务、敌人少量掉落和出售多余装备。主要支出为药品、基础装备与可选的补给。商店价格和掉落速度要保证玩家完成前两次任务后能买到一次有感知的提升，同时不因购买药品而陷入无法继续游戏的状态。

首版商人采用固定货架：武器、护甲、饰品、药品各若干件。购买时校验金币和背包容量；出售时校验物品可售性；交易完成立刻刷新金币、库存和 UI。若“商城”实际指联网付费商店，这一模块需要另立产品、支付、合规和服务端方案，不纳入本版。

### 6.6 任务与关卡

**演示任务示例：夺回密信**。据点商人委托玩家取回一份密信；主目标是进入营地、获取密信并撤离。可选目标是解救俘虏或收集补给。

- “影”的自然路径：观察巡逻 → 标记守卫 → 从侧面潜入 → 取得密信 → 撤离。
- “锋”的自然路径：正门破防 → 逐区清理 → 击败精英守卫 → 取得密信。
- 混合路径：潜入到中庭后暴露，利用环境和战斗能力继续完成任务。

关卡需有清楚的入口、目标区、撤离点和至少两个可辨识路线。任务阶段、目标标记及失败/完成条件都应可在 UI 中确认。

### 6.7 敌人与掉落

| 敌人 | 战术作用 | 核心行为 | 克制点 |
| --- | --- | --- | --- |
| 近战杂兵 | 教会闪避与基础连击 | 近身追击、单次攻击、短暂硬直 | 两名主角均可处理 |
| 警戒/远程兵 | 迫使玩家改变站位 | 远程攻击、发现后呼叫附近队友 | “影”可绕后，“锋”可借掩体推进 |
| 精英守卫 | 检验破防、资源管理 | 格挡、强攻击、有限连招 | “锋”正面破防，“影”利用路线避开或先削弱 |

击败敌人给予少量经验/金币，装备掉落以固定或低随机概率为主。首版避免靠重复击杀刷最优装备。敌人应有最大追击范围、脱战逻辑和可恢复的巡逻状态。

### 6.8 基础 UI 与交互

- **主菜单**：开始/继续、设置、退出。
- **HUD**：生命、耐力、当前主角、技能冷却、药品数量、任务目标、警戒提示、锁定目标状态。
- **背包/装备**：分类、属性对比、装备/卸下、金币数量。
- **商店**：购买/出售页、单价与总价、无法交易原因、交易结果反馈。
- **任务**：目标、阶段、可选目标、奖励预览。
- **暂停/设置**：音量、画面质量、镜头灵敏度、键位提示；后续再考虑完整改键。
- **结算**：完成目标、奖励清单、继续/返回据点。

UI 设计重点是战斗时低干扰，菜单中信息清楚。所有可点击操作应有悬停、不可用和成功/失败反馈；关键文本避免只靠颜色传达。

### 6.9 存档与状态一致性

至少保存：两名主角的等级和属性、装备/背包、金币、任务进度、商店状态、所处关卡或据点。进入任务前保存基线，完成结算后再提交奖励，可减少重复领取和物品丢失。存档载入后检查装备引用、物品数量和任务状态是否合法。

## 7. 操作建议（键鼠）

| 操作 | 建议按键 | 备注 |
| --- | --- | --- |
| 移动 / 镜头 | WASD / 鼠标 | 常见第三人称习惯 |
| 轻击 / 重击 | 鼠标左键 / 右键 | 如右键用于锁定，则需调整 |
| 闪避 / 蹲伏 | 空格 / Ctrl | 具体键位以试玩为准 |
| 交互 / 使用药品 | E / Q | 避免与技能冲突 |
| 切换主角 | Tab 长按或快捷键 | 仅在允许切换的状态生效并给出原因 |
| 背包 / 暂停 | I / Esc | 菜单打开时停止或减缓游戏待定 |

键位只是原型起点，应在角色控制方案确定后统一调整。手柄映射需另做一轮可用性测试。

## 8. 内容规模与制作资产

首版预计需要：两名主角及各自动作集、三类敌人及其关键动作、一处据点与小型商人区域、武器/护甲/饰品若干、基础音效与界面图标。若采用现成资源，先统一比例、骨架、动画风格和授权范围，再投入系统制作。

**内容最小化原则**：用关卡路线、敌人组合、主角能力差异增加深度；不要用大量装备名称和重复任务代替玩法。

## 9. 开发顺序与阶段验收

| 阶段 | 交付物 | 通过条件 |
| --- | --- | --- |
| 0. 工程盘点与定稿 | 确认引擎版本、现有资产、目标平台、团队与时间；锁定 MVP | 本文“待确认事项”有明确答案 |
| 1. 手感灰盒 | 双主角移动、切换、攻击/防御、一个敌人 | 两人操作差异可感知，连续游玩无流程阻断 |
| 2. 关卡与敌人 | 灰盒据点、三类敌人、潜入警戒 | 主目标能用至少两条路线完成 |
| 3. RPG 闭环 | 装备、掉落、经验、商店、任务奖励、存档 | 从任务到成长再到下一次挑战完整可用 |
| 4. UI 与表现 | HUD、菜单、动画/音效、视觉提示 | 新玩家能在无口头指导下完成演示任务 |
| 5. 平衡与稳定 | 调整数值、修复卡关、性能检查 | 目标设备上流畅，存读档与交易无丢失/重复 |

不要在阶段 1 尚未验证战斗与切换手感时大量制作装备和剧情资产。每阶段保留一个随时可玩的版本，以便及时发现系统连接处的问题。

## 10. 主要风险与取舍

1. **双主角成本接近两套角色系统**：通过共用基础动作、交互和 UI，只在核心能力上分化来控制成本。
2. **潜入与战斗互相抢资源**：同一个关卡同时验证两种路线，避免先单独做完一套再拼接。
3. **动作表现依赖动画资产**：灰盒期先确定碰撞、时机和反馈，再换高质量动画。
4. **装备数值过早膨胀**：先验证有限装备能否改变战术选择，再增加词条与品质。
5. **开放世界范围失控**：首版使用封闭但多路线的据点，待闭环稳定后再决定地图规模。
6. **商店经济失衡**：用固定库存和可预测奖励建立基线，随后根据试玩记录调整。

## 11. 需要由项目负责人决定的方向

这些决定会直接影响设计和工期，建议在进入开发前确定：

1. 世界观：历史题材、架空历史，还是完全原创奇幻世界？是否明确避开与参考作品接近的时代与视觉符号？
2. 项目规模：个人/团队人数、可投入时间、目标发布日期及可用资产预算？
3. 战斗侧重：偏写实、讲究招架与破防，还是偏爽快、重连招与技能？
4. 切换方式：只在非战斗状态切换是否满足预期？是否必须加入战斗中切换？
5. 商城含义：纯游戏内商人，还是计划真实货币商品？
6. 叙事比重：任务驱动的轻叙事，还是有大量过场与角色关系的剧情 RPG？
7. 目标平台与输入方式：PC 键鼠即可，还是首版必须覆盖手柄/主机？

## 12. 下一步建议

先确认第 11 节的关键取舍，并盘点工程现有内容。随后将本讨论稿更新为 v1.0：锁定世界观、两名主角的具体技能、演示关卡地图草图、装备与敌人的首批数据表，以及可执行的阶段任务清单。代码实现应从第 1 阶段的灰盒原型开始。
